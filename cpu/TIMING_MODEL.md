# CPU/GPU behavioral timing model

This file is intentionally the same in Gemini, PCcheck, and checkpointing.
The checkpoint algorithms themselves are not reimplemented here.

## Rule 1: keep real CPU-visible work real

Filesystem writes, fsync/msync, sockets, Gloo communication, process/thread
synchronization, checkpoint metadata, and Python/C++ control flow execute for
real. They are not replaced by sleeps.

## Rule 2: replace accelerator-only storage with a device surrogate

A CUDA allocation is redirected to a distinct CPU allocation with the same
shape, dtype, numel, and therefore logical byte size. The allocation is tagged
as a device surrogate. A host checkpoint/staging buffer is a different CPU
allocation. This matters because collapsing the two would make GPU-to-host
capture a no-op.

Equivalent idea:

    CUDA: GPU/HBM buffer -> host DRAM buffer
    CPU : surrogate DRAM A -> checkpoint DRAM B

The physical memory technologies differ; the software-visible source/destination
separation and byte count are preserved.

## Rule 3: preserve values unless values are explicitly irrelevant

The compatibility layer copies values when .cuda()/.to("cuda") is redirected.
Garbage payloads may be created by a workload when payload contents are
irrelevant, but the compatibility layer itself does not silently destroy
control values such as sizes, ranks, counters, versions, or metadata.

## Rule 4: GPU/host transfer timing is exact-size calibrated

`gpu_compat.py` records the real CPU copy duration C. If a GPU profile contains
an exact-size measured target T for the same transfer kind and byte count, the
compatibility layer waits max(0, T-C). The visible duration is therefore:

    max(real CPU surrogate operation, measured GPU target)

No interpolation or bandwidth extrapolation is performed. In strict mode a
missing exact-size timing is an error.

## Rule 5: GPU compute functions use named measured durations

`gpu_timing_capture.py` runs on a real GPU and records CUDA-event durations for
explicitly named serialized GPU compute functions. It writes median duration
and sample count to a profile. `function_timing.py` runs the original CPU-callable
function and adds only residual delay. Missing function names fail in strict
mode.

Typical names are workload-specific, for example `forward`, `backward_compute`,
and `optimizer_step`. They are not hard-coded because the original repositories
do not expose identical training functions.

## Rule 6: communication is not mocked

NCCL process-group initialization is redirected to Gloo on CPU-only VMs. The
actual PyTorch distributed send/recv/collective calls remain intact. Therefore
real network bytes are generated by the original communication path.

A measured NCCL duration may be applied around the original communication
function only when the boundary is known and doing so does not double-count a
transfer already calibrated elsewhere. Real Gloo time is never discarded; the
same max(real, target) rule applies.

## CUDA event capture boundary

`GpuTimingCapture` measures work ordered between CUDA events on the measured
stream. It should be used for serialized GPU compute phases. It must not be used
to measure independently overlapping streams and then replay those durations as
serial sleeps, because that would double-count overlap.

## Stream behavior

The shared `gpu_compat.py` provides synchronous fake CUDA stream/event APIs as
the conservative default. That is correct for the two checkpoint capture paths
that explicitly block:

- PCcheck performs `cpu_ar.copy_(gpu_ar)` in its checkpoint pipeline before the
  batch advances.
- checkpointing baseline performs `host_buf.copy_(gpu_buf, non_blocking=False)`
  and then synchronizes before transmitting the checkpoint.

Gemini is different. Its original DeepSpeed path places
`tensor_on_cpu.copy_(tensor, non_blocking=True)` on a dedicated checkpoint copy
stream. The Gemini repository therefore adds `cpu/gemini_stream_compat.py`.
When entered inside `CpuGpuCompat`, that adapter schedules nonblocking copies on
a single worker representing Gemini's copy stream and returns control to the
caller immediately. Stream synchronization drains the pending copy work. The
original `SnapshotOptimizer` source is not modified.

This preserves the important blocking/nonblocking distinction, but it is still
a software surrogate rather than a physical model of CUDA DMA engines or GPU
stream scheduling.

## What a valid result may claim

The CPU experiment may claim preservation of software-visible checkpoint
control flow, logical buffer sizes, real host/network/storage operations, and
calibrated durations at explicitly measured boundaries.

It must not claim physical equivalence to HBM, PCIe/NVLink, CUDA DMA engines,
NCCL kernels, GPU scheduling, or overlap that was not explicitly represented by
the CPU compatibility layer.
